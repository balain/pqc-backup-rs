# PQROOT02 root-key format

**Status:** frozen root-key encoding version 1  
**Byte order:** unsigned integers are big-endian  
**Total length:** 62 bytes

The `PQROOT02` magic identifies the key family. The internal version is `1`; it is independent from the `PQBACK02` archive version.

## Layout

| Offset | Size | Field | Meaning |
| ---: | ---: | --- | --- |
| 0 | 8 | magic | ASCII `PQROOT02` |
| 8 | 2 | key-format version | `1` |
| 10 | 16 | root-key ID | stable opaque identifier |
| 26 | 4 | root-key epoch | deployment-defined unsigned epoch |
| 30 | 32 | root secret | uniformly random secret bytes |

No trailing bytes are allowed.

## Semantics

The root-key ID is not secret and adds no entropy. It SHOULD be randomly generated once for a root-key lineage or assigned by a documented inventory process. The same ID MAY be retained across planned epoch rotations only when the deployment policy defines the ID as a lineage identifier. A deployment MAY instead assign a fresh ID to every root secret; it must apply one interpretation consistently.

The epoch distinguishes rotations within the selected policy. Annual numeric values such as `2026` are recommended for simple deployments. Rotate immediately after suspected compromise or custody failure.

The 32-byte root secret MUST be generated by a cryptographically secure random generator. It MUST NOT be a password, UTF-8 phrase, hash of a human secret, or reused from unrelated applications.

## Storage

The complete file is secret because it contains the root secret. On supported Unix targets, this implementation creates it with mode `0600`. Operators must also protect its parent directory, backups, snapshots, removable media, and redundant custody copies.

The root-key file MUST be kept separately from the ML-KEM decapsulation seed and encrypted archives. Retain it while any required archive names its ID and epoch.

## Validation

A decoder MUST require:

- exactly 62 bytes;
- exact magic;
- key-format version 1;
- a root-key ID and epoch matching the archive before attempting recovery;
- successful AEAD authentication, which is authoritative.

The visible archive ID/epoch is untrusted until AEAD verification succeeds.

## Compatibility

Changing field order, size, encoding, or interpretation requires a new root-key magic or key-format version. Parsers MUST reject unknown versions rather than guessing.
